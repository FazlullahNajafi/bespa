# 10 — Implementation plan (React Native + Expo)

How to get from an empty repo to Bespa v1 in the field. The spec settles *what*; this
document settles *in what order, with which tools, and what "done" means at each step*.

It assumes the phasing of [09](09-roadmap-and-risks.md) (~19 weeks, one full-stack dev +
part-time design) and re-sequences a few things for engineering reasons, called out in
[§10.9](#109--deliberate-deviations-from-the-spec-phasing).

---

## 10.0 Decisions to lock before the first line of code

Four of the open questions in [§9.4](09-roadmap-and-risks.md) have **long lead times** and
block Phase 0 exit. Start the paperwork in week 1, in parallel with coding.

| # | Decision | Why it blocks | Recommendation |
|---|---|---|---|
| 1 | **SMS / OTP provider** | Indian transactional SMS requires **DLT registration** (entity + header + template approval, typically 1–3 weeks). Phone verification is a Phase 0 exit criterion. | MSG91 or an Indian-routed Twilio. File DLT on day 1. Design so that Google sign-in plus a *deferred* phone verification is a valid state — never let SMS block sign-up. |
| 2 | **Google OAuth client + SHA-1** | Android Google sign-in needs the release keystore SHA-1, which EAS generates. Needed before any on-device test of social login. | Run `eas credentials` in week 1; register both the debug and the EAS release SHA-1. |
| 3 | **Play Console + App Store accounts** | The Play internal-testing track is how pilot users install builds. Account/org verification can take weeks. | Open both in week 1. Get a hello-world build onto the internal track by week 3. |
| 4 | **Pilot villages + geo seed source** | `geo_units` is the tenancy spine; every RLS policy keys off it. Nothing is testable without real rows. | Baroo plus two villages that differ in size and distance from town. Import LGD codes, hand-correct. |

Two more can wait, but not long: **Purgi orthography** (before any `bft.json` string is
written) and **stats provenance** (before the stats UI ships).

| Language | TypeScript `strict: true`; no `any` in `src/api/` | |

### Scaffolding into this repo

The repo is non-empty (`spec/`), so `create-expo-app` needs a detour:

```bash
npx create-expo-app@latest .bespa-tmp --template default && cp -r .bespa-tmp/. . && rm -rf .bespa-tmp
```

Then `npx supabase init`, `npx supabase start`, and write migration `0001`.

guarantee when we own the primitives. No charting library either: the two chart shapes the
spec calls for (donut, bar) are about 150 lines of `react-native-svg`.

## 10.3 Repo scaffold

Extends [§2.5](02-architecture.md) with the files that actually get written first.

The SDK 57 template puts routes under `src/app/` with an `@/*` alias onto `src/`, rather
than the root-level `app/` of [§2.5](02-architecture.md). We follow the template — one
source root is tidier than two, and fighting the default buys nothing.

```
src/
├── app/                      # expo-router routes: (auth), (tabs), village/, trip/, admin/
├── lib/
│   ├── supabase.ts           # client + chunked SecureStore session adapter
│   ├── database.types.ts     # generated, committed
│   ├── queryClient.ts        # TanStack Query + AsyncStorage persister
│   ├── outbox/               # SQLite queue, background task, idempotency keys
│   ├── errors.ts             # PG errcode / machine string -> i18n key
│   ├── hijri.ts              # tabular base + local offset, unit-tested
│   ├── geo.ts                # ltree path helpers, ancestor checks
│   └── net.ts                # connectivity + Lite mode detection
├── api/                      # one module per domain; TanStack hooks only
│   ├── keys.ts               # the single query-key factory
│   ├── village.ts  places.ts  gallery.ts  directory.ts  notices.ts
│   ├── trips.ts    seats.ts   presence.ts bookings.ts
│   └── calendar.ts helplines.ts issues.ts
├── theme/tokens.ts           # doc 08 colour / type / spacing, light + dark
├── components/               # the primitives from §8.5
├── features/                 # screen-local logic, one folder per module
└── i18n/{en,ur,bft}.json
supabase/
├── migrations/               # 0001_geo.sql, 0002_identity.sql, ...
├── functions/                # push-fanout, verify-phone, forward-issue, ...
├── seed/                     # geo units, helplines, calendar, departments
└── tests/                    # pgTAP: one file per RLS policy family
```

**Four rules that keep this from rotting:**

- Screens never import `supabase` directly. Every read and write goes through `src/api/*`.
- Every mutating call goes through the outbox wrapper, **even when online** — one code
  path, so offline is not a special case that only gets exercised on a plane.
- Query keys come from `keys.ts` only. No inline string arrays.
- Every Postgres error is mapped in `errors.ts` before it can reach a component.

## 10.4 The spine — build in this exact order

These six layers are mutually dependent, and everything else sits on top. Weeks 1–3.

1. **Migrations 0001–0003: geo, identity, privacy.** `geo_units` with the `ltree` path
   trigger, `profiles`, `privacy_settings`, `contact_access_log`, and the
   `is_covillager()` / `administers()` helpers from [§6.3](06-data-model.md). Seed real
   Kargil geography immediately — no fixtures; the shape of real data is the point.
2. **The pgTAP RLS harness — before any content table exists.** Fixtures: two villages, a
   member in each, a panchayat admin, a district admin, an anon. Every policy family gets a
   test asserting both the allow *and* the deny. Wired into CI. This is the
   highest-leverage thing in Phase 0: privacy is risk #4, and the policy set becomes
   untestable by hand very quickly.
3. **Supabase client + auth.** Session persisted through a **chunked SecureStore adapter** —
   SecureStore's per-item limit is smaller than a JWT session blob, and phones are shared
   in this region, so AsyncStorage-in-the-clear is the wrong default. Auth state in
   Zustand; route guards in `app/(auth)/_layout.tsx`.
4. **Query client + offline persistence.** Persister hydrated *before* first render, 7-day
   TTL, with a per-query `meta.persist` opt-out so trips and seat maps are never restored
   from disk (spec: stale seat availability is worse than none).
5. **The outbox.** SQLite table `(id, idempotency_key, kind, payload, media_paths, attempts,
   created_at)`, a background task that drains on reconnect, exponential backoff, and a
   `PendingChip` bound to its state. Media uploads first, then the RPC is called with the
   returned `media.id`, so a retry after a partial failure does not re-upload.
6. **Theme, i18n, navigation shell.** Tokens, the primitives with a dev gallery route at
   `app/_dev/`, `i18next` with `en` complete and `ur`/`bft` stubbed, and **`I18nManager`
   RTL wired on day 1** — it needs an app reload to take effect, so build that prompt now
   rather than in Phase 4 when it becomes a forty-screen layout audit.

On **`hijri.ts`**: implement the tabular civil algorithm in-repo rather than pulling a
library, wrap it behind `getLocalHijriDate(geoUnitId, date)` which applies the district
offset, and unit-test it against a table of known Kargil dates supplied by a local scholar.
It is roughly 60 lines, and it is risk #3 — owning it is cheaper than auditing a dependency.

## 10.5 Phase plan

Each phase lists the work, the **spike** that de-risks it, and a hard exit criterion. Exit
criteria are the spec's, sharpened into things that can be observed.

### Phase 0 — Foundation (3 weeks)

The six spine layers above, plus: sign-up / sign-in / Google / phone-OTP screens, the
cascading geo picker, profile edit, the privacy screen as its own onboarding step (§3.4),
EAS dev-client builds on both platforms, EAS Update channels, Sentry, and a GitHub Actions
job running typecheck + lint + jest + pgTAP.

- **Spike (2 days): seat concurrency.** Write `hold_seats` / `book_seats` and hammer them
  with a concurrent script (pgbench, or 50 parallel clients) asserting zero double-bookings
  and correct partial-hold semantics. Doing this in week 2 rather than week 14 means the
  entire Transport module is designed against a proven primitive.
- **Exit:** a real user on a real phone signs up, verifies a phone, picks Minjee, sets their
  number to "villagers only", force-quits, reopens offline, and still sees their profile.
  pgTAP proves a Trespone member cannot read that phone number. A build installs from the
  Play internal track.

### Phase 1 — Village (4 weeks)

Home with its nine independently-empty-able sections; village profile and stats with the
source-and-year rule; places submit → moderate → browse → map, including the 150 m duplicate
check; gallery with admin banner selection; directory with `get_member_contact`, its rate
limit and its audit log; notices with composer, push, and WhatsApp deep-link sharing; the
moderation queue.

- **Spike (1 day): the image pipeline on 2G.** Pick → resize to ≤1600px → upload → CDN
  transform → render, measured on a throttled connection with a real 4 MB photo.
- **Exit:** three pilot villages populated with real content by real sarpanches, with no
  developer touching the database. Home cold-starts to first paint in under 4s on a 2 GB
  Android.

### Phase 2 — Civic (3 weeks)

Dual calendar, month grid and event detail; the `hijri_offsets` admin control with its
audit trail; scholar-reviewed seed events; helplines bundled in the binary *and* served
live; `submit_issue` with duplicate detection; the admin triage queue; `forward-issue`
composing a WhatsApp deep link; the issue timeline; the public issues board with upvotes.

- **Spike (1 day): bundled-seed override.** Prove a fresh install in aeroplane mode dials a
  helpline, and that the server copy cleanly supersedes the bundled copy when newer.
- **Exit:** ten real issues forwarded to real departments, three closed with a response. A
  local scholar signs off on the Hijri dates shown for the current and next month.

### Phase 3 — Transport (6 weeks — the long pole)

Routes, stands, driver onboarding and admin verification, vehicles, `seat_layouts` as data,
trip creation under 45 seconds plus "repeat this trip", the SVG seat map with four states,
glyphs and accessibility labels, hold/book/release/cancel against Realtime, bookings with
the six-character code, no-show and cancellation handling, ratings with tags, the QR payment
screen, the live stand board with presence, the −1-seat notification action and soft claims,
and trust & safety (reports, SOS, phone-number visibility windows).

- **Spike (2 days): the persistent driver notification.** Two interactive actions that
  mutate server state from a locked screen, on Android *and* iOS. This is the most
  platform-fragile requirement in the spec (§4.4) and deserves proof before the module is
  designed around it. If iOS cannot carry it, the fallback is a Live Activity or a plain
  reopen-the-app flow — decide from evidence, in week 1 of the phase.
- **Exit:** 20 verified drivers on Kargil↔Baroo, 100 completed seat claims, **zero
  double-bookings in production**, and a seat greying out on a second device within ~1s.

### Phase 4 — Hardening & launch (3 weeks)

Performance pass on a 2 GB Android; a full offline pass in aeroplane mode through every
flow; the VoiceOver/TalkBack audit on the five critical paths; Urdu localisation and the RTL
layout audit; privacy policy and Play data-safety declarations; `account-delete`; analytics
review; closed beta; public release.

- **Exit:** ≥99.5% crash-free sessions across the beta, every §1.7 launch metric
  instrumented and reporting, both stores approved.

## 10.6 Engineering standards

| Area | Standard |
|---|---|
| **Performance budgets** | Cold start to Home <4s on a 2 GB Android over 3G; list scroll ≥55fps on FlashList; JS bundle <4 MB; no screen issues more than 3 network requests on mount |
| **Testing** | Unit: `hijri.ts`, `errors.ts`, outbox retry/idempotency, seat-layout rendering. SQL: pgTAP per policy family plus the booking transaction. E2E (Maestro): sign-up → village pick → privacy; browse → hold → book → cancel; report an issue offline → reconnect → it appears. Those three are where a regression costs trust. |
| **Error handling** | RPCs raise stable machine strings; `errors.ts` maps them to i18n keys; a raw Postgres message reaching a user is a bug with a test |
| **Accessibility** | Enforced in the primitives (44×44pt minimum baked into `Button`), audited per §8.6 |
| **Analytics** | PostHog; event names in one `src/lib/events.ts`; **no PII, ever** — no phone, no name, no precise location |
| **Migrations** | Forward-only, reversible where cheap, never edited after merge |
| **Feature flags** | A `feature_flags` table read at launch and cached — lets Transport ship dark to pilot villages before the driver cohort exists |

## 10.7 Release & CI/CD

- **Channels:** `development` (dev client, local Supabase) · `preview` (staging, internal
  testers) · `production`.
- **OTA policy:** EAS Update for JS-only changes; a native change (new module, permission,
  SDK bump) means a store build. Because the pilot cohort is on slow connections, ship OTA
  aggressively and store builds rarely — that is precisely why Expo was chosen (§2.1).
- **CI (GitHub Actions):** on PR — typecheck, lint, jest, pgTAP against a Supabase service
  container, and a check that `database.types.ts` matches the migrations. On merge to
  `main` — EAS Update to `preview`.
- **Store prep starts in Phase 0, not Phase 4:** package name, icons, splash, permission
  strings with plain-language reasons, and a published privacy-policy URL. A late store
  rejection is the classic way a 19-week plan becomes 23.

## 10.8 Critical path

```
DLT / SMS paperwork ────────────┐
Play + Apple account verify ────┤
Google OAuth + SHA-1 ───────────┼──▶ Phase 0 exit ──▶ Phase 1 ──▶ Phase 2 ──┐
geo seed (LGD + correction) ────┘                                           │
                                                                            ▼
seat concurrency spike (P0) ─────────────────────────────▶ Phase 3 ──▶ Phase 4 ──▶ launch
driver recruitment via stand unions (starts in Phase 2) ─┘
```

The two things that slip this schedule are **not code**: SMS/DLT approval and driver
recruitment. Both must start weeks before the code that depends on them. Driver onboarding
in particular is in-person work (§4.7) — begin it during Phase 2 so Phase 3 ships into a
cohort that already exists.

## 10.9 Deliberate deviations from the spec phasing

| # | Change | Why |
|---|---|---|
| 1 | EAS dev client, store accounts and the internal-testing track move from Phase 4 into **week 1** | Store and credential surprises are late-breaking and unbounded; the pilot cohort needs an install link long before launch |
| 2 | The pgTAP RLS harness is built **before** the first content table | Privacy is risk #4, and the policy set stops being hand-testable at about table eight |
| 3 | The seat-concurrency RPCs are spiked in **Phase 0** rather than discovered in Phase 3 | The whole Transport UX rests on partial-hold semantics; knowing them early changes the seat-map design |
| 4 | RTL and font scaling are handled in the **primitives, in Phase 0** | Retrofitting RTL across forty screens in Phase 4 is a week; building it into 15 primitives is a day |
| 5 | The persistent driver-notification spike happens at the **start** of Phase 3 | It is the most platform-fragile requirement in the spec; the fallback must be chosen from evidence, not discovered at the end |
| 6 | Weather stays out of v1 entirely (already optional in §3.1) | It is the only third-party runtime dependency in the Village module and it earns nothing at launch |

4. Migration `0001` — `geo_units` plus the `ltree` trigger; seed Kargil district from LGD.

6. `eas credentials` → SHA-1 → Google OAuth client registered.
7. Supabase client with the chunked SecureStore session adapter; the sign-up screen.
8. Book the local scholar review for the Hijri seed data — Phase 2, long lead.
